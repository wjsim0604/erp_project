FLOW ERP · ENGINEERING GUIDE

기술과 아키텍처 안내

프로젝트, 업무, 일일 보고를 관리하는 사내 웹 애플리케이션의 기술 구성과 주요 데이터·요청 흐름을 정리했습니다.

문서 기준: 현재 저장소 구현 · 주요 스택: Next.js 14 · TypeScript · MySQL 8
목차
한눈에 보기기술 스택아키텍처 요청 흐름주요 기능인증과 보안 데이터 구조운영과 한계포트폴리오·면접코드 위치

한눈에 보기

화면과 서버 API가 하나의 Next.js 애플리케이션에 있습니다. 브라우저 요청을 서버에서 인증·권한 확인·입력 검증한 뒤 TypeORM을 통해 MySQL에 반영합니다.

화면과 API가 한 앱에

Next.js App Router가 서버 페이지, 클라이언트 UI, JSON API를 함께 제공합니다.

역할에 따른 접근 제어

시스템 역할과 프로젝트별 역할을 함께 확인해 프로젝트 데이터를 제한합니다.

명시적 스키마 변경

TypeORM 자동 동기화를 끄고 버전 관리되는 마이그레이션으로 DB를 변경합니다.

외부 연동은 선택 설정

AI, 이메일 알림, 장애 알림은 환경변수가 연결된 경우에만 사용합니다.

애플리케이션 아키텍처

서버 로직은 데이터 접근과 인증, 감사 기록, 알림, 파일 처리를 작은 모듈로 나눕니다. 파일 본문은 DB 대신 비공개 파일 저장소에 둡니다.

일반 요청 흐름

  1. 사용자가 화면에서 프로젝트·업무·보고서 데이터를 요청하거나 수정합니다.
  2. Next.js API가 Auth.js 세션을 확인하고, 활성 사용자 계정을 DB에서 재확인합니다.
  3. 요청 본문을 Zod로 검증하고 시스템 역할 및 프로젝트 멤버십을 검사합니다.
  4. TypeORM이 MySQL에서 데이터를 읽거나 저장합니다. 파일 업로드는 비공개 저장 경로에 저장합니다.
  5. 중요 변경은 감사 로그에 기록하고, 해당 이벤트의 알림 설정에 따라 앱 알림 또는 웹훅 전달을 시도합니다.
  6. JSON 응답을 받아 React 화면이 갱신됩니다.

가입과 로그인

공개 회원가입은 없습니다. 관리자가 만든 48시간 유효 초대 링크로 사용자가 계정을 생성합니다. 첫 관리자는 명령행의 npm run admin:create로 생성합니다. 로그인은 이메일과 비밀번호를 사용하고, MFA가 켜진 관리자는 인증 코드 또는 복구 코드도 입력합니다.

보고서용 AI 초안

사용자가 입력한 메모를 설정된 OpenAI 호환 API에 보내 초안을 받습니다. 초안은 자동 저장되지 않으며 사용자가 확인해 적용합니다. AI 연결 정보가 없으면 수동 보고 기능은 계속 쓸 수 있습니다.

주요 기능

영역동작
대시보드서울 날짜 기준 오늘의 보고 제출 여부, 내 업무, 마감·지연 업무, 접근 가능한 프로젝트를 요약합니다.
프로젝트와 업무멤버십에 따라 프로젝트를 노출합니다. 프로젝트 관리자는 업무 상세 필드를 편집하고, 담당자는 자신의 업무 상태를 변경할 수 있습니다.
일일 보고날짜별 보고와 프로젝트 연결 항목을 저장하고 제출합니다. 관리자와 프로젝트 관리자의 보고 조회 범위가 다릅니다.
문서프로젝트 권한을 확인해 문서를 업로드·다운로드·삭제합니다. PDF, 텍스트, CSV, 이미지와 Office 파일을 지원합니다.
검색·알림사용자에게 허용된 프로젝트·업무를 검색합니다. 업무 배정, 보고 제출, 보고 댓글 알림을 사용자별로 조정합니다.
관리직원 초대, 역할·계정 활성화 관리, 관리자 MFA 설정을 제공합니다.

인증과 보안

세션

JWT 세션, 최대 수명 8시간. 보호된 API에서 활성 계정을 다시 확인합니다.

로그인 제한

이메일 해시별 15분 내 실패 5회를 제한합니다.

관리자 MFA

TOTP 비밀은 AES-256-GCM으로 암호화합니다. 복구 코드는 SHA-256 해시로 저장하고 각 코드를 한 번만 사용합니다.

API 권한·요청 제한

프로젝트 멤버십과 역할을 서버에서 검사하며 민감한 API는 DB 기반 요청 제한을 사용합니다.

파일 경로

파일 키를 검증하고 공개 웹 폴더 밖에 저장합니다. 파일 이름은 경로 구분자와 제어 문자를 제거합니다.

감사 기록

프로젝트·사용자·업무·문서 관련 주요 변경을 감사 로그에 남깁니다.

운영 키 관리: MFA를 켜기 전에 `MFA_ENCRYPTION_KEY`에 무작위 base64 32바이트 키를 설정하고, 운영 DB와 분리해 안전하게 백업해야 합니다.

테이블과 TypeORM 엔티티는 src/server/entities.ts에, 스키마 변경 이력은 src/server/migrations에 있습니다. synchronize와 자동 마이그레이션 실행은 꺼져 있습니다.

운영과 한계

  • CI: GitHub Actions에서 MySQL을 띄우고 마이그레이션과 Next.js 빌드를 수행하도록 구성했습니다.
  • 헬스 체크: /api/health가 앱과 DB 연결을 확인합니다. PowerShell 점검 스크립트는 실패 알림 웹훅을 지원합니다.
  • 백업·복구: PowerShell 백업 스크립트는 DB 덤프, 업로드 아카이브, SHA-256 매니페스트를 생성합니다. 복구 훈련은 별도 복구 DB를 대상으로 실행하도록 설계됐습니다.
  • 배포: CI만 설정돼 있습니다. 실제 배포는 프로젝트의 운영 플랫폼이 정해지지 않아 연결되지 않았습니다.
  • 이메일: 내장 SMTP는 없습니다. 알림 이메일은 `NOTIFICATION_WEBHOOK_URL`에 연결한 신뢰 가능한 메일 릴레이가 담당합니다.
  • 파일 저장: 기본 저장소는 서버 로컬 파일 시스템입니다. 여러 앱 인스턴스를 운영하면 공유 영속 저장소가 필요합니다.
  • 검증 상태: 최근 코드 변경 이후 빌드·테스트와 실제 복구 훈련은 아직 실행하지 않았습니다.

배포 전에는 백업 → 대기 마이그레이션 확인 → 마이그레이션 적용 → 빌드·배포 → 헬스 체크 순서로 진행하고, 주기적으로 격리 복구 훈련을 수행합니다.

포트폴리오 소개와 예상 면접 질문

30초 프로젝트 소개

“Flow ERP는 팀의 프로젝트와 업무, 일일 보고를 한곳에서 관리하는 사내 웹앱입니다. Next.js와 TypeScript로 화면과 API를 구성하고, MySQL·TypeORM으로 데이터를 관리했습니다. 특히 프로젝트별 권한 검사를 API 서버에 두고, 관리자 MFA, 감사 로그, 파일 권한 검사와 명시적 DB 마이그레이션을 구현해 업무 기능과 운영 보안을 함께 고려했습니다.”

1. 이 프로젝트에서 가장 중요하게 고려한 설계는 무엇인가요?

답변 예시: “권한을 화면 표시만으로 처리하지 않고 API에서 매 요청마다 확인하는 점입니다. 사용자의 전체 역할과 프로젝트 멤버십을 함께 검사하고, 프로젝트 관리자는 관리 프로젝트에 연결된 보고 항목만 볼 수 있게 범위를 제한했습니다. 화면은 편의성을 위한 것이고 최종 접근 제어는 서버에서 수행하도록 했습니다.”

2. 왜 Next.js 안에 화면과 API를 함께 구성했나요?

답변 예시: “이 앱은 사내 업무 도구 MVP라서 프론트엔드와 API를 한 프로젝트에서 관리하는 편이 구현·배포 흐름을 단순하게 만들었습니다. App Router의 서버 페이지와 Route Handler를 기능 단위로 정리했습니다. 규모가 커지거나 여러 클라이언트가 같은 도메인 API를 쓰기 시작하면 API를 별도 서비스로 분리할 수 있게 데이터 접근과 서버 로직을 모듈화하는 방향을 고려할 수 있습니다.”

3. 권한 검사는 어떤 순서로 이뤄지나요?

답변 예시: “먼저 Auth.js 세션에서 사용자 ID를 확인하고 DB에서 계정이 활성 상태인지 확인합니다. 그 다음 시스템 역할과 프로젝트 멤버십을 확인한 뒤, 요청한 데이터가 그 프로젝트에 속하는지 검사합니다. 예를 들어 담당자는 자기에게 배정된 업무의 상태를 바꿀 수 있고, 프로젝트 관리자는 업무 상세 필드를 편집할 수 있습니다.”

4. 스키마 변경에 TypeORM synchronize를 쓰지 않은 이유는 무엇인가요?

답변 예시: “운영 DB 구조가 애플리케이션 실행 시점에 예기치 않게 바뀌는 일을 막기 위해서입니다. 변경 내역을 마이그레이션 코드로 리뷰하고, 배포 전에 대기 마이그레이션을 확인한 뒤 명시적으로 적용하도록 했습니다. MySQL DDL은 자동 롤백을 기대하기 어려워 백업과 실패 후 점검 절차도 운영 문서에 포함했습니다.”

5. 관리자 MFA와 복구 코드는 어떻게 보호하나요?

답변 예시: “TOTP 비밀은 서버 환경의 32바이트 키를 사용해 AES-256-GCM으로 암호화해 저장합니다. 복구 코드는 원문 대신 SHA-256 해시만 저장하고, 사용 시 조건부 갱신으로 한 번만 소비되게 합니다. 암호화 키를 잃으면 기존 TOTP 비밀을 복호화할 수 없으므로 별도 백업과 운영·스테이징 키 분리를 안내합니다.”

6. 문서 파일은 왜 DB에 저장하지 않았나요?

답변 예시: “DB에는 프로젝트, 업로더, 파일 유형, 크기, 저장 키 같은 검색·권한 확인용 메타데이터를 보관하고 파일 본문은 비공개 파일 저장소에 둡니다. 저장 키는 서버가 생성하고 경로를 검증하며, 프로젝트 권한 확인 후 파일을 제공합니다. 여러 앱 서버에서 운영할 때는 공유 영속 저장소가 필요하고 DB와 파일을 같은 백업 시점으로 맞춰야 합니다.”

7. AI 기능은 업무 데이터 노출을 어떻게 줄이나요?

답변 예시: “AI 초안 요청에는 사용자가 입력한 메모만 외부 OpenAI 호환 API로 보냅니다. 직원·프로젝트 전체 데이터나 DB 레코드를 함께 전달하지 않고, 생성 결과도 자동 저장하지 않습니다. 사용자가 검토하고 직접 적용하도록 해 생성 결과를 확정된 업무 기록과 구분했습니다.”

8. 실제로 겪은 DB 마이그레이션 문제와 해결은 무엇인가요?

답변 예시: “알림 설정 테이블을 추가할 때 MySQL이 `user_id`와 `users.id`의 외래 키 타입이 호환되지 않는다고 거절했습니다. 새 테이블이 DB 기본 collation을 사용하고 기존 `users` 테이블은 `utf8mb4_0900_ai_ci`를 명시한 점을 원인으로 보고, 마이그레이션에 같은 문자셋과 collation을 지정했습니다. 코드 수정 후 실제 운영 DB에서 재실행·검증하는 절차는 별도로 필요합니다.”

9. 현재 구현의 한계와 다음 개선 순서는 무엇인가요?

답변 예시: “코드에는 CI 워크플로와 운영 스크립트를 추가했지만 실제 CI 실행, 통합 테스트, 복구 훈련은 아직 확인하지 않았습니다. 다음에는 권한·보고 저장·문서 접근 경로를 우선 자동 테스트하고, 격리 DB에서 마이그레이션과 복구 훈련을 검증하겠습니다. 운영 배포 플랫폼을 정한 뒤 배포 파이프라인과 공유 파일 저장소도 연결할 계획입니다.”

면접 전 확인할 체크리스트

  • 직접 작성·수정한 코드 범위와 팀 작업 범위를 정확히 설명합니다.
  • 실제 실행하지 않은 빌드·테스트·배포·복구 훈련은 완료했다고 말하지 않습니다.
  • DB 마이그레이션 이슈는 원인, 수정 내용, 아직 필요한 검증을 나눠 설명합니다.
  • 실제 배포 주소나 사용량이 없다면 운영 성과 수치를 만들지 않습니다.
  • 면접 전 주요 API 하나를 선택해 인증, 입력 검증, 권한 검사, DB 쓰기 흐름을 코드로 따라가 봅니다.
